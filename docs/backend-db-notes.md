# Что понять на примере этого задания

Этот список помогает проверить знания. По одному репозиторию нельзя точно определить,
какие темы уже освоены: попробуйте объяснить каждую без подсказки.

## 1. Pydantic-схема и ORM-модель

`TaskIn` описывает JSON от клиента: заголовок и приоритет. Pydantic проверяет его
до вызова обработчика. Пустой заголовок или приоритет 6 дают ответ 422.

`Task` описывает таблицу `tasks`. Экземпляр `Task` связан с работой SQLAlchemy:
его можно добавить в сессию, загрузить из БД, изменить или удалить.

`TaskOut` описывает ответ API. Он содержит ещё и `id`.
`from_attributes=True` позволяет Pydantic читать поля ORM-объекта через атрибуты.

Практика: найдите ограничение длины заголовка в схеме и определение столбца в модели.
Почему одной валидации запроса недостаточно, если в БД пишет другой скрипт?
Учтите: SQLite не обеспечивает ограничение длины только из-за `String(100)`.

## 2. Engine, SessionLocal, Session

| Объект | Зачем нужен |
| --- | --- |
| `engine` | Подключает SQLAlchemy к конкретной БД и управляет соединениями |
| `SessionLocal` | Фабрика, которая создаёт сессии |
| `db`, экземпляр Session | Загружает объекты и отслеживает изменения в рамках операции |

Engine создаётся один раз. `get_db()` открывает отдельную сессию для запроса
и закрывает её после использования. Контекстный менеджер также освобождает ресурсы
и откатывает незавершённую транзакцию при закрытии.

`yield db` отдаёт сессию FastAPI, а затем выполнение зависимости продолжается
и сессия закрывается. Возврат сессии без механизма закрытия оставил бы ресурс открытым.

Практика: проследите путь от `Depends(get_task_service)` до `get_db()`.
Объясните, какой объект получит конструктор репозитория.

## 3. Что происходит при создании задачи

```python
task = Task(**data.model_dump())
db.add(task)
db.commit()
db.refresh(task)
```

Создание Python-объекта само по себе ничего не сохраняет.
`add()` регистрирует новый объект в сессии.
Во время `commit()` SQLAlchemy выполняет необходимые SQL-запросы и фиксирует транзакцию.
`refresh()` перечитывает сохранённые поля из БД, включая назначенный идентификатор.

При изменении уже загруженного объекта повторный `add()` обычно не нужен:
сессия отслеживает изменения его атрибутов.

Практика: временно уберите `commit()` в отдельной локальной ветке и проверьте,
появится ли запись после следующего запроса. Затем верните код.

## 4. Транзакция, commit и rollback

Транзакция объединяет изменения, которые должны примениться вместе.
`commit()` подтверждает изменения. `rollback()` отменяет ещё не подтверждённые изменения.
После commit отменить запись обычным rollback уже нельзя.

Здесь один запрос изменяет одну задачу, поэтому commit находится в репозитории.
Если одна операция должна создать задачу и записать связанное событие, обычно
нужна общая транзакция для обеих записей: ошибка во второй не должна оставить первую.
После ошибки flush/commit сессию надо откатить перед повторным использованием;
в нашем запросе ошибка завершает работу, а контекстный менеджер закрывает сессию.

Практика: опишите, что должно произойти, если задача сохранилась,
а запись обязательного события упала. Где в таком варианте должен быть commit?

## 5. CRUD на SQL и SQLAlchemy

| Операция | Пример SQL | В нашем коде |
| --- | --- | --- |
| Create | `INSERT INTO tasks ...` | `db.add(task)`, затем commit |
| Read одного | `SELECT ... WHERE id = 1` | `db.get(Task, task_id)` |
| Read списка | `SELECT ... ORDER BY id` | `db.scalars(select(Task).order_by(Task.id))` |
| Update | `UPDATE tasks SET title = ... WHERE id = 1` | Изменение атрибутов, затем commit |
| Delete | `DELETE FROM tasks WHERE id = 1` | `db.delete(task)`, затем commit |

`id` назначает БД. Формула `len(tasks) + 1` может создать одинаковые идентификаторы
после удаления элемента из середины списка. Идентификаторы не обязаны идти без пропусков.

Практика: создайте три задачи, удалите среднюю, создайте ещё одну.
Проверьте, что у оставшихся задач разные id и их заголовки не изменились.

## 6. HTTP-контракт

POST создаёт задачу и отвечает 201. GET возвращает данные с 200.
PUT заменяет редактируемые поля задачи. В нашем контракте пропущенный priority
при PUT сбрасывается на значение по умолчанию 3. Для изменения только переданных
полей можно отдельно добавить PATCH с частичной схемой и `exclude_unset=True`.
DELETE отвечает 204 и не возвращает JSON.

404 означает, что задачи с таким id нет. 422 означает, что запрос не прошёл
валидацию. Это разные ситуации: при 422 обработчик эндпоинта обычно ещё не запускался.

Практика: сравните ответы на `/tasks/999999` и `/tasks/abc`.
Предскажите статус до отправки каждого запроса.

## 7. Слои и Depends

Роут принимает HTTP-параметры и вызывает сервис. Сервис проверяет существование
задачи и выбирает операцию. Репозиторий выполняет запросы к БД.
В простом CRUD бизнес-правил мало, но здесь сохранена структура учебного проекта.

Depends сообщает FastAPI, как получить необходимые объекты.
Функции в `dependencies.py` собирают сессию, репозиторий и сервис для запроса.
Их можно заменить в тестах без переписывания эндпоинтов.

Практика: устно пройдите весь путь запроса PUT от JSON до SQL и обратно.
На каком этапе можно получить 422, на каком 404 и когда выполняется commit?

## 8. create_all и миграции

`create_all()` создаёт отсутствующие таблицы. Он не переносит автоматически все
изменения ORM-модели в существующую таблицу. Для развития схемы обычно применяют
миграции Alembic: это последовательность версионируемых изменений БД.

SQLite хранит данные в локальном файле. PostgreSQL работает отдельным сервером.
Общий принцип работы с моделями и сессиями переносится, но драйвер, настройки,
поведение типов и ограничения БД могут отличаться.

Практика: объясните, почему добавление столбца в Python-модель не гарантирует,
что этот столбец появился в уже существующей базе.
