# Task Tracker на FastAPI

Учебное задание: интеграция БД и полный CRUD сущности `Task`.
Приложение находится в `task_app/`. Данные задач хранятся в SQLite через SQLAlchemy.

## Запуск

Python 3.10 или новее. Команды выполняются из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r task_app/requirements.txt
python -m uvicorn task_app.main:app --reload
```

В Windows вместо `source` используйте `.venv\Scripts\activate`.

Swagger UI: <http://127.0.0.1:8000/docs>.
Файл `tasks.db` создаётся автоматически в корне репозитория при запуске.
Данные сохраняются после остановки сервера. Отдельный сервер БД не нужен.

Для этого задания достаточно `task_app/requirements.txt`.
Корневой `requirements.txt` относится также к другим учебным примерам.

## Эндпоинты

| Метод | URL | Действие | Успешный ответ |
| --- | --- | --- | --- |
| POST | `/tasks` | Создать задачу | `201`, созданная задача |
| GET | `/tasks` | Получить все задачи | `200`, список задач |
| GET | `/tasks/{task_id}` | Получить одну задачу | `200`, задача |
| PUT | `/tasks/{task_id}` | Заменить данные задачи | `200`, обновлённая задача |
| DELETE | `/tasks/{task_id}` | Удалить задачу | `204`, без тела |

У задачи три поля: `id` назначает БД, `title` содержит от 1 до 100 символов,
`priority` — число от 1 до 5 (по умолчанию 3).
Пробелы по краям заголовка удаляются, пустой заголовок запрещён.
В POST и PUT передаются только `title` и `priority`.
PUT заменяет все редактируемые данные: если `priority` не передать, он станет 3.
Неизвестные поля и неверные данные возвращают `422`, отсутствующая задача — `404`.

Пример тела POST или PUT:

```json
{
  "title": "Сдать задание по бэкенду",
  "priority": 2
}
```

Пример ответа после создания:

```json
{
  "title": "Сдать задание по бэкенду",
  "priority": 2,
  "id": 1
}
```

## Проверка перед сдачей

1. Запустить сервер и открыть `/docs`.
2. Создать две задачи через POST и запомнить их `id`.
3. Проверить GET списка и GET одной задачи.
4. Изменить заголовок и приоритет одной задачи через PUT.
5. Перезапустить сервер и проверить, что изменения сохранились.
6. Удалить задачу через DELETE и убедиться, что GET возвращает `404`.
7. Отправить `priority: 6` и проверить ответ `422`.

## Автоматические проверки

```bash
python -m pip install -r task_app/requirements-dev.txt
python -m unittest discover -s tests -v
```

Тесты проверяют CRUD, валидацию, отсутствие задачи, работу с несколькими задачами
и сохранение изменений после повторного запуска приложения.
Они используют временную БД и не меняют ваш `tasks.db`.

## Где находится код

| Файл | Ответственность |
| --- | --- |
| `task_app/database.py` | Engine, сессии, создание таблицы |
| `task_app/models/models.py` | ORM-модель и таблица `tasks` |
| `task_app/schemas/tasks.py` | Форматы запросов и ответов, валидация |
| `task_app/repositories/tasks.py` | Чтение и запись в БД |
| `task_app/services/tasks.py` | Операции с задачами, проверка существования |
| `task_app/dependencies.py` | Сборка зависимостей через Depends |
| `task_app/api/v1/tasks.py` | HTTP-эндпоинты |
| `task_app/main.py` | Запуск приложения и подключение роутеров |

В этом учебном варианте таблица создаётся через `Base.metadata.create_all()`.
При дальнейшем изменении существующей таблицы понадобятся миграции, например Alembic.

Роуты пользователей оставлены как отдельный пример с хранением в памяти.
Папки `db/` и `DI/`, а также `server.py` содержат другие учебные примеры.

Разбор основных понятий и упражнения: [docs/backend-db-notes.md](docs/backend-db-notes.md).
